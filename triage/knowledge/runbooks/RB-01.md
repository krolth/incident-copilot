title: Revert a bad deploy, config push, or migration
category: bad_change
---
## When to use
Errors, latency, or resource use got worse within minutes of a change, and the onset lines up with that change.
A change is any of: a service deploy, a `cfgpush` config or feature-flag push, or a `chess-db-migrate` migration.
Mitigate first (revert); find and fix the defect afterwards.

## Find the change
- Deploy history lists service deploys and `chess-db-migrate` runs. It does **not** list config pushes: check the
  `config-agent` log (`config applied: <key> ... by <user>`) for the same window.
- Compare the change time with the first bad minute, not with the alert time; alerts fire minutes after onset.
- Only hosts or pods on the new version or config misbehave. Compare per-host error rate and version.
- A dependency (redis-live, chess-db) can look unhealthy only because the changed service is sending it more
  traffic, for example after a retry or pool-size change. Check the dependency's request rate: if it jumped while
  user traffic stayed flat, the change is the cause and the dependency is the victim.

## Revert: stateless services
gateway, accounts, matchmaking, leaderboards, stats, anticheat.
1. `deploy rollback <service>` (about 5 minutes), or `cfgpush revert <change-id>` for a config push (under 1 minute).
2. Watch error rate and p99 latency for 10 minutes; recovery should line up with the revert time.

## Revert: game servers (stateful)
Restarting or redeploying a game-server host aborts or migrates the live games on it. Do not restart them to fix a
bad version.
1. Mark the old version current in matchmaking's allocator so new games go only to hosts on the old version.
2. Cordon every host on the bad version (no new games). Watch `active_games` fall as games finish.
3. If the bad version is actively breaking games (crashes, clock errors), migrate its remaining games instead of
   waiting: check first that the old version can read the checkpoint format the new version wrote. If it cannot,
   escalate to Play on-call before migrating; migrated games would abort.
4. Reinstall the old version on drained hosts and uncordon them one at a time.
A config push to game servers only affects new games unless the key is live-reloadable; cordon and drain as above
if running games must stop using it.

## Revert: database migrations
A migration cannot be undone by redeploying a service.
1. If the migration was additive (new index, new nullable column), it can usually be reverted with its down step;
   page Data on-call to run it.
2. If it was destructive or rewrote data, do not revert. Mitigate in the application (roll back the service that
   uses the new shape, or turn off its flag) and forward-fix with Data on-call.
3. A new index that makes queries slower: drop it `CONCURRENTLY`, never inside a long transaction on the primary.

## After mitigation
- Open a ticket for the change owner with the change id, onset time, and evidence. Do not re-apply it until fixed.

## Do not
- Restart or scale out first. It hides the cause, and on game servers it aborts players' games.
- Roll back a different, earlier change because it is the only one in deploy history; check config pushes too.
