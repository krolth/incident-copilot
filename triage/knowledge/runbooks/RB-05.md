id: RB-05
title: Drain and replace an unhealthy node
category: infra_failure
---
## When to use
One machine is unhealthy while the rest of the fleet is fine: a game-server VM, a Kubernetes node, or a database
host. The machine may be failing (hardware, kernel) or starved by something else running on it. Mitigate by moving
work off it; investigate the machine afterwards.

## Signals
- Errors or latency concentrate on one host name (`gs-04`) or on pods scheduled on one Kubernetes node, while the
  same service on other hosts is healthy.
- Hardware or kernel messages on that host: disk I/O errors, filesystem remounted read-only, NIC resets, kernel
  soft lockups.
- Kubernetes node: CPU pegged by pods of another service. Anticheat workers have no CPU limits and share the
  general node pool, so an analysis burst can starve gateway, accounts or matchmaking pods on the same node.
  Compare the struggling pods' node with the node's top CPU consumers.
- Health checks flapping for one target; service-wide metrics only mildly degraded.

## Steps
1. Identify the unhealthy machine from per-host errors, or from the node the struggling pods share.
2. Move work off it:
   - Kubernetes node: `kubectl cordon <node>` then `kubectl drain <node>`; pods reschedule on healthy nodes. If a
     noisy neighbour caused it, scale anticheat down or pause `anticheat-backfill` so it does not starve the next node.
   - game-server VM: cordon it in the allocator; if the host is failing, migrate its games (they resume from
     checkpoints in redis-live) rather than waiting for them to finish.
   - database host: page Data on-call; replica promotion is theirs.
3. Replace or reimage the machine, verify it rejoins healthy, uncordon.
4. Confirm the error rate is back to baseline; open a hardware ticket, or a ticket to isolate anticheat on its own
   node pool with CPU limits.

## Do not
- Roll back the service that alerted when only the pods on one node are affected.
- Restart the whole fleet for a single-host problem.
